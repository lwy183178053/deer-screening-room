# 媒体哈希文件名与标题映射设计

## 目标

保留现有工作室目录结构，将每个视频文件改为稳定的短哈希文件名；原始显示名称写入媒体根目录的映射表，节点扫描时恢复标题。这样 Windows Docker 不需要枚举超长中文文件名，播放仍读取实际文件。

## 约束与决策

- 工作室一级目录不变，只修改视频文件名。
- 映射文件固定为媒体根目录 `.deer-media-map.json`，不进入 Git 或镜像。
- 哈希使用原始规范化相对路径的 SHA-256，文件名格式为 `media-<64位小写十六进制>.<原扩展名>`。
- 映射以哈希文件名为键，记录工作室、原始文件名、原始相对路径和展示标题；文件移动到其他工作室时仍能恢复原始标题。
- 媒体键使用 `original_path` 计算，而不是使用当前哈希文件名；文件改名后保持同一媒体键，避免目录记录和权益断开。
- 重命名采用同目录原子替换；目标已存在且不是同一文件时停止该文件，不覆盖任何文件。
- 映射写入采用临时文件加原子重命名；写入失败时保留原文件名并报告扫描错误。
- 新文件只有在大小连续两次检查一致后才处理，避免下载中的文件被重命名。

## 平台边界

Windows Docker 的 bind mount 在目录枚举阶段可能直接返回 `readdirent ... input/output error`，容器无法看到超长原始文件名。因此 Windows 端必须由宿主机 PowerShell 使用 Windows 文件 API 预处理文件；节点容器只负责读取已经标准化的文件和映射表。Linux/NAS 节点可以在扫描时直接标准化可枚举的新文件。

## 数据流

1. 宿主机或节点发现未标准化的视频。
2. 计算目标哈希名，确认目标不存在后在原工作室目录内重命名。
3. 更新 `.deer-media-map.json`。
4. 扫描器读取短文件名、映射标题并生成媒体键、封面和目录清单。
5. Gateway 只保存媒体键和展示字段，不保存或暴露原始文件路径。

## 失败与回滚

- 任一文件重命名或映射写入失败，不删除、不覆盖源文件，记录具体路径并停止当前批次。
- 迁移前备份映射表、节点海报缓存和 Compose 配置；原始视频内容不做转码或删除。
- 回滚时停止节点，将哈希文件按映射表恢复原始文件名，再恢复旧 Compose 和节点镜像；映射表保留到回滚验证结束。
